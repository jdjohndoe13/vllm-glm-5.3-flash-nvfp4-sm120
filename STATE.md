## Workflow rules (ssh / windows quirk)
- ssh: `C:\Windows\System32\OpenSSH\ssh.exe -o BatchMode=yes user@testcomp2`. Wrap possibly-hanging remote cmds in `timeout 10/12`. Passwordless sudo available.
- **No `$()` inside grep args** (reads stdin, hangs). `awk` broken locally → `cut`/`grep -o`+`tr`. Local md5: `certutil -hashfile <file> MD5`. Remote: `md5sum`.
- **pgrep trap**: never put another clause containing literal `canary5m.sh` in the same ssh command as a `pgrep -f` check (self-matches wrapper → false CANARY_ALIVE).
- **`bash -c "cd X && nohup … & sleep 3; …"` backgrounding trap**: the trailing `&` backgrounds the WHOLE `cd && nohup` list — subsequent `;`-separated relative-path commands run in the ORIGINAL cwd and ENOENT spuriously (looks like script death when nothing died). Correct launch one-liner: `ssh … "cd /mnt/data/.../logs/canary && nohup bash canary5m.sh >/dev/null 2>&1 </dev/null &"` (nothing after the `&`). The nohup'd child survives ssh-session teardown (HUP-immune) — verify liveness via station.pid + `kill -0`, not by the launching session's return.
- **station.pid is written by the LAUNCHER step** (`echo <pid> > station.pid` after verified launch), not by canary5m.sh itself — after any restart, align it and verify `kill -0 $(cat station.pid)`.
- Engine restarts are user-owned in the launch window (§7); canary handles rebase autonomously.
